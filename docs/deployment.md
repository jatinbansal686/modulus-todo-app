# Deploying the API

MongoDB Atlas (free M0) for the database, Render (free web service) for the API.

Both steps need a browser and an account, so they are written as a runbook rather
than a script. Everything that _can_ be declared in code already is — see
[`render.yaml`](../render.yaml).

Total time: ~20 minutes, most of it waiting for the first build.

---

## 1. MongoDB Atlas

1. Create a free account at `cloud.mongodb.com`.
2. **Create a cluster** → **M0 Free**. Pick the region closest to
   `Singapore`, to match the Render region.
3. **Database Access** → add a database user.
   - Authentication: password. Use Atlas's "Autogenerate Secure Password" and copy it.
   - Role: **Read and write to any database**. Not Atlas Admin — the API only ever
     touches its own database, and a scoped user means a leaked credential cannot
     reconfigure the cluster.
4. **Network Access** → add IP `0.0.0.0/0`.

   > This looks alarming and is deliberate. Render's free tier has **no static
   > outbound IP** — the documented egress ranges are shared across every service in
   > the region, and dedicated egress is a paid feature, so there is no narrower rule
   > that would work. What actually protects the database is SCRAM authentication and
   > a user scoped to one database. VPC peering is the production answer, and the
   > README says all of this out loud rather than quietly opening the database.

5. **Connect** → **Drivers** → copy the connection string. It looks like:

   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?retryWrites=true&w=majority
   ```

   Substitute the real password, and **insert the database name** before the `?`:

   ```
   mongodb+srv://USER:PASSWORD@CLUSTER.mongodb.net/modulus_todo?retryWrites=true&w=majority
   ```

   ⚠️ Without `/modulus_todo` the driver connects to the `test` database. Everything
   works, and the data is silently in the wrong place.

## 2. Render

1. Create a free account at `render.com` and connect the GitHub account that owns
   this repo.
2. **New** → **Blueprint** → select `modulus-todo-app`.
   Render reads `render.yaml`; there is nothing to configure by hand except one value.
3. When prompted for `MONGODB_URI`, paste the Atlas string from step 1.5.
   The three secrets are generated by Render itself and never leave it.
4. **Apply**. The first build takes ~3–5 minutes: `npm ci` compiles argon2 from
   source.

> **If the build fails with `sh: 1: nest: not found`**, the build command is missing
> `--include=dev`. Render sets `NODE_ENV=production`, npm honours that by omitting
> devDependencies, and the compiler (`@nestjs/cli`, TypeScript) lives there. The
> blueprint already accounts for this; the note is here because the install step
> _succeeds_ and reports a believable package count before the build dies, so the
> error points at the wrong thing.

### Verify

```bash
API=https://modulus-todo-api.onrender.com   # your actual URL

# 1. Liveness — expect {"status":"ok","database":"connected",...}
curl -s $API/health

# 2. Readiness — expect {"status":"ready",...}. If this says not-ready while
#    /health says degraded, MONGODB_URI is wrong or the Atlas allowlist is missing.
curl -s $API/health/ready

# 3. Seed the demo account and ten tasks dated relative to now
curl -s -X POST $API/api/v1/demo/reset

# 4. Full auth round trip
curl -s -X POST $API/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"demo@modulusseventeen.com","password":"ModulusDemo2026!"}'
```

Swagger is at `$API/docs`.

Check the deploy log for **`Indexes synchronised for: User, RefreshToken, Task`**.
`autoIndex` is off in production, so this line is the only thing that creates the
unique email constraint, the unique refresh-token hash and the token TTL. Its absence
means those guarantees are missing — see `src/database/sync-indexes.ts`.

## 3. Point the mobile app at it

Already done — `apps/mobile/src/shared/config/env.ts` reads:

```ts
const PROD_API_URL = 'https://modulus-todo-api.onrender.com';
```

Only change this if the service is recreated under a different name.
`assertProductionUrlConfigured()` throws on launch in a release build if the value is
ever reverted to a placeholder, so a release APK cannot ship pointing at nothing.

`DEV_API_URL` stays on `10.0.2.2:3000`, so debug builds keep talking to a local API.
To point a debug build at the hosted one temporarily, change that constant and reload
the bundle — no rebuild needed, since it is plain JavaScript.

## What to expect on the free tier

- **Cold starts.** The instance spins down after ~15 minutes idle and takes up to a
  minute to wake. The first request after a quiet period is slow. The mobile client
  is built for this: a 30-second request timeout, and a splash screen capped at 1.5s
  after which the app renders and finishes authenticating in the background.
- **Slow logins.** Render free gives 0.1 CPU. Argon2id at OWASP's parameters
  (m=19MiB, t=2, p=1) needs ~40–50ms on a full core, which becomes several hundred
  milliseconds under a 10% CPU quota — so expect roughly 0.5–1s for a warm login.
  The parameters are kept anyway; weakening password hashing to flatter a free tier
  is the wrong trade, and naming the constraint is better than hiding it.
- **Memory.** Argon2 runs on libuv's threadpool, capped at 4 threads by default, so
  peak hashing memory is about 4 × 19MiB ≈ 76MiB inside the 512MB limit. Do **not**
  raise `UV_THREADPOOL_SIZE` — that is how you manufacture an out-of-memory problem
  that does not currently exist.
